### Latency analysis

The latency increase (19s → 28s average) is attributable to:

1. **Larger corpus retrieval** — 185 chunks vs 17 means denser embedding space, more candidates evaluated per query
2. **Richer synthesis context** — 5 retrieved chunks at ~130 words each = ~650 words of context vs ~130 words previously, Claude synthesis takes longer
3. **Synthesis model unchanged** — Claude Sonnet 4.6 accounts for ~15-25s of every query
4. **ST encoding unchanged** — all-MiniLM-L6-v2 encodes query in ~100-200ms (negligible)

## Operational Recommendations

1. **Latency reduction** — 28s average is synthesis-dominated. Streaming (`/rag/stream`) would reduce perceived latency to first token. ST encoding (~200ms) and Qdrant search (~50ms) are already fast.

2. **Corpus expansion** — 185 chunks covers 12 domains well but each domain has ~15 chunks. Target 50 chunks/domain (600 total) for production depth. Local PDF download + Railway upload bypasses IP restrictions.

3. **Embedding upgrade** — all-MiniLM-L6-v2 (384-dim) is fast but imprecise for technical aerospace text. BGE-M3 (1024-dim, multilingual) or E5-large-v2 would improve retrieval precision. Requires GPU or model serving endpoint.

4. **Reranking** — adding a cross-encoder reranker (ms-marco-MiniLM) on top of the dense retrieval would improve precision of top-5 chunks, reducing hallucination guard warnings.

5. **Redis** — once healthy, response caching would eliminate repeat query latency (same question within 1 hour returns cached answer in <100ms).
